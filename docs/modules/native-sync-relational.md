# 原生同步结构化存储

本次调整以每批 100 条照片记录、从请求开始到本地应用完成不超过 1 秒为目标。验收记录端到端时间及 HTTP、接收保存、配对、应用耗时，不用单条查询时间代替批次时间。

云图与同步持久化状态使用普通 SQLite 列及关联表。图片、原图记录、接收中的记录、版本、摘要、资源大小、修改事件和恢复捕获不得保存在 JSON/BLOB 文档中。HTTP wire JSON 和进程内 DTO 不属于持久化存储。已有未提交工作、未知提交结果和发布恢复证据必须保留。

- `sync_entries` 继续是本地义务和身份的唯一主记录；本地事件与摘要使用独立列。
- 已确认照片的元数据和双资源描述使用结构化照片状态；接收中的 Master/Asset 只保存未完成的记录，完成后清除，不重新引入全量远端镜像。
- 接收记录头的 job、record ID、photo ID、master ID、版本和相对路径可直接索引查找。wire 字段使用有类型的值列；资源和引用分别使用明确列，不保存序列化对象。
- 账号能力、配置草稿、分页进度、已发出操作、冲突与文件发布捕获同样使用结构化状态，数组使用有序关联行；全局关闭意图使用 `sync_reset_state` 的 token/error 列。
- 保持账号、配置代际、本地版本和水位检查；普通接收不得清除并发编辑。
- 已有开发数据库在一个事务中转换，转换失败回滚，不通过清空历史或重新上传恢复计数。数据库开发版本仍为 1。

常用索引至少覆盖 `(job_id, native_photo_id)`、`(job_id, native_master_id)`、`(job_id, relative_path)`、接收记录 ID／所属照片 ID、资源身份和发布所属照片。通过实际查询计划验证，不仅检查索引名称。

服务端 wire 契约仍由 [协议链接索引](native-sync-protocol.md) 指向的 SyncServer 仓库拥有。

## 2026-10-18 验证

使用实际服务、真实数据库副本和生产接收／DbActor 路径，在 Debug 构建下连续接收 10 批、每批 100 条已有本地确认关系的照片记录：请求到合并、进度落库平均 448.08 ms，最慢 591.37 ms，全部低于 1 秒。HTTP、保存、应用和 checkpoint 都包含在批次计时内。验证不启动上传或原图／缩略图传输，不改真实图库数据库。

旧库首次结构转换在该数据副本上实测 12.36 秒，仅发生一次。后续打开和正常批次不重复转换；状态转换与整批性能分别记录。字段／索引测试、真实双客户端资源旅程和旧状态回滚覆盖独立于性能样本，不把这些样本宣称为所有网络和文件大小下的延迟保证。
