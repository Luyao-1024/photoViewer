## P0：文件安全

### P0-01 文件 URI 拼接可能操作错误文件

- [x] 已完成
- 证据：**已复现路径解析错误**；未通过删除真实文件验证影响。
- 位置：[扫描器](../src/core/backend/local.rs)、[回收站](../src/core/trash.rs)、[缩略图路径解析](../src/core/thumbnails/cache.rs)、[查看器](../src/ui/viewer/stage.rs)。

扫描器直接拼接 `file://`，而回收站通过 GIO 解析 URI。两套路径语义不一致：

| 原文件名 | GIO 解析直接拼接的 URI 后得到的文件名 |
|---|---|
| `photo%20one.jpg` | `photo one.jpg` |
| `photo%23one.jpg` | `photo#one.jpg` |
| `photo#one.jpg` | `photo` |
| `photo?.jpg` | `photo` |

对应路径存在时，可能移动错误对象。应统一通过标准 API 转换路径与 URI，同步处理数据库已有 URI、缩略图缓存和查看器解析逻辑，避免只修复一个调用点。

验收重点：包含 `%`、`#`、`?`、空格和中文的文件名往返一致；两个容易被混淆的文件同时存在时，只能操作用户选中的对象。

### P0-02 回收站精确匹配失败后仍猜测同名文件位置

- [x] 已完成
- 证据：**代码确认**。
- 位置：[trash.rs](../src/core/trash.rs)，`resolve_trash_entry_in_roots`、`prepare_permanent_delete_in_roots`。

精确匹配 `.trashinfo` 失败后，代码仍返回首个回收站根目录中的同名路径，永久删除也使用这个结果。如果该位置恰好有另一个来源的同名文件，可能删除无关对象。

建议：无法确认条目身份时返回明确错误；破坏性操作不得使用猜测路径。显示缩略图所需的降级行为也应与删除、恢复路径区分。

验收重点：目标条目缺失、元数据损坏或失配时，即使回收站存在同名文件，也不得恢复或删除那个无关文件。

## P1：功能正确性与测试基线

### P1-01 扫描变更检测使用创建时间，漏掉同大小修改

- [x] 已完成
- 证据：**已复现**。
- 位置：[local.rs](../src/core/backend/local.rs)，`file_index_time` 和扫描短路判断。

当前优先使用 `created()`，而不是 `modified()`。本次修改 JPEG 的 EXIF，保持文件大小不变，实际修改时间已经变化，但重新扫描返回 `0`，数据库仍保留旧拍摄时间。

建议：分离照片排序日期与文件变化版本；后者使用真实修改时间及足够精度，并与缩略图失效判断保持一致。

验收重点：同大小内容修改能够重新索引；快速连续修改、EXIF 修改和缩略图失效得到覆盖。

### P1-02 无权限访问被误判为文件不存在

- [x] 已完成
- 证据：**已复现**。
- 位置：[local.rs](../src/core/backend/local.rs)，`collect_missing_live_media_under_roots`。

临时子目录失去读取权限后，仍然存在的两张照片被列入索引删除计划。这里删除的是数据库记录，不是照片文件，但可能连带丢失收藏等状态。

建议：区分 `NotFound`、权限错误及存储不可用，仅对确定不存在的文件清理索引；根目录可读不代表所有子目录都可读。

验收重点：权限拒绝、挂载暂时不可用时保留索引和用户状态；确实删除的文件仍能正常对账。

### P1-03 编辑保存缺少元数据保留策略

- [x] 已完成
- 证据：**已复现 EXIF 丢失**；ICC 等其他元数据需要补充验证。
- 位置：[save.rs](../src/core/edit/save.rs)，`encode_sibling`、`edited_metadata`。

带 EXIF 的 JPEG 保存副本后，副本不再包含 EXIF，数据库却继续保留原拍摄时间，形成文件与数据库不一致。

建议：明确拍摄日期、相机信息、ICC 等元数据的保留规则；像素方向已经烘焙后，应单独处理方向标记；GPS 是否保留可以作为导出选项。对动画、动态照片、HDR 被转换为普通静态图的情况，也应明确保存语义。

验收重点：保存副本、覆盖保存和重新扫描后，文件与数据库的日期、方向等信息一致；有意丢弃的信息对用户可见。

### P1-04 可预览编辑的格式不一定能够保存

- [x] 已完成
- 证据：**已确认保存解码路径不支持 HEIC**。
- 位置：[editor_panel.rs](../src/ui/editor_panel.rs)，`load_source_async`；[save.rs](../src/core/edit/save.rs)，`load_source_image`。

编辑预览通过 GdkPixbuf 加载，保存通过 `image` crate 重新解码。仓库中的真实 HEIC 样本在保存解码路径上返回 `Unsupported`。

建议：建立查看、编辑、编码能力表，支持 HEIC 导出 JPEG／PNG，或在进入编辑前明确限制，避免用户完成操作后才发现无法保存。

验收重点：所有开放编辑入口的格式都有可用保存方案，或在操作前清楚提示限制。

### P1-05 相册复制／移动的一致性保护不完整

- [x] 已完成
- 证据：**数据库失败遗留副本已复现**；并发覆盖窗口及跨文件系统限制为代码确认。

注入数据库写入失败后，复制操作返回错误，但目标文件仍然存在。目标命名使用“先检查不存在，再 copy／rename”，并发时仍有覆盖窗口；相册移动缺少跨文件系统处理。批量操作中途失败时，也需要准确反馈已成功的部分。

建议：复用编辑保存中的临时文件、禁止覆盖发布及失败回滚模式；统一重命名、复制和移动的文件安全约束，提供逐项成功／失败结果。

验收重点：数据库失败、目标冲突、并发操作、跨分区移动及回滚失败均有明确结果，不覆盖无关文件，不把部分成功报告成完全未执行。

### P1-07 扫描失败未完整传递到调用者

- [x] 已完成
- 证据：**已复现**。
- 位置：[local.rs](../src/core/backend/local.rs)，批量入库错误处理；[app.rs](../src/app.rs)，初始化错误反馈。

数据库拒绝插入时，扫描仍返回 `Ok(0)`，失败只进入日志，使“没有新照片”和“照片全部入库失败”无法区分。编辑源图加载失败等路径也主要记录日志，用户反馈仍有改进空间。

建议：返回包含成功、跳过、失败数量的扫描结果；在用户界面提供可见的错误、必要的详情和重试入口，避免失败表现为空内容或无响应。

验收重点：全部失败、部分失败和没有变化有不同结果；用户能够知道失败并采取下一步操作。
